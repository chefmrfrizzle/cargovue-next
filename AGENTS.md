# CargoVue repository rules

These instructions apply to every person, script, AI assistant, and automated agent working in this
repository.

## Mission

Build a neutral, traceable, human-governed LNG evidence workspace whose released outputs can be
independently verified.

## Hard boundaries

1. **No legacy source-code copying.** Old repositories are research inputs only. A behavior enters
   this repository through `docs/MIGRATION_LEDGER.md`, a new specification, and new tests.
2. **No unauthorized science.** Never add or execute a formula, conversion, tolerance, correction,
   lookup table, uncertainty model, or physical constant unless an active method profile identifies
   its authority, edition, scope, units, implementation, reviewer, validation evidence, and expiry.
3. **AI proposes; humans dispose.** Extraction, classification, chronology, linkage, and narrative
   generated by AI remain proposals until an authorized reviewer accepts or corrects them.
4. **Neutral language only.** Do not determine legal liability, insurance coverage, sanctions status,
   fraud, causation, certification, cargo conformity, or professional negligence.
5. **Exact provenance.** Material statements must point to an immutable source and an exact page,
   cell, range, timestamp, or region. A filename alone is not a citation.
6. **Fail closed.** Missing authorization, tenant context, evidence, keys, scan results, review,
   retention status, or release approval must stop the action.
7. **Separate trust zones.** Public, workspace, portal, evidence worker, PCE, and offline verifier
   communicate through versioned contracts. Do not create direct database shortcuts.
8. **Synthetic development only.** Real customer, vessel, cargo, claim, employee, or counterpart data
   is forbidden until the production-data gate is formally approved.
9. **No secrets in Git.** Use named environment variables and managed secret stores. Example values
   must be obviously local or fake.
10. **Determinism before cleverness.** Custody, audit, state transitions, manifests, comparison, and
    release behavior must be deterministic and testable.

## Required workflow

Before implementing a change:

- read the product charter, relevant ADRs, and trust-boundary documentation;
- identify the affected tenant, custody, AI, scientific, review, and release boundaries;
- add acceptance, refusal, misuse, and cross-tenant tests;
- use exact decimal representations for commercial or measured quantities;
- update the contract version when a message shape changes;
- record a new ADR when the decision is difficult to reverse.

Before completing a change, run `npm run verify` and report any skipped or unavailable check.

## Forbidden shortcuts

- silent schema upgrades or ignored unknown fields;
- floating-point arithmetic for contractual quantities;
- default tolerances presented as LNG standards;
- mutable source evidence;
- unsigned release marked as verified;
- portal access to draft workspace records;
- agent access to signing keys;
- production fallbacks to in-memory persistence;
- copying copyrighted standards text into the repository;
- weakening a test to make an implementation pass.

## Prompt use

Prompts under `docs/prompts/` are job instructions, not sources of truth. Product and architecture
decisions belong in normal documentation and ADRs. If a prompt conflicts with this file, this file
wins.
